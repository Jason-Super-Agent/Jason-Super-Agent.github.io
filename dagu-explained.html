Dagu 是一款本地优先（local-first）、单二进制自托管的工作流引擎，用声明式 YAML 定义任务依赖图（DAG），内置 Web UI，不需要额外数据库或消息队列。

Dagu 是什么

Dagu 的核心定位是一个轻量级 DAG 调度与执行引擎：你用 YAML 文件描述一组任务（steps）之间的依赖关系，Dagu 负责按依赖顺序执行、重试失败步骤、记录日志、可视化运行状态，并支持 cron 定时调度。

它以单一可执行文件的形式发布，可在 Linux、macOS、Windows 上直接运行，也可以用 Docker 或 Helm 部署到 Kubernetes。任务本身可以是 shell 命令、Docker 容器、Kubernetes Job，或通过 SSH 在远程主机上执行的命令。

项目在 GitHub 上目前约 4k star、300+ fork，属于活跃维护中的开源项目，采用"开源核心 + 可选自托管许可证"模式：社区版免费自托管，付费许可证额外提供 SSO、RBAC、审计日志等企业能力。

为什么会出现 Dagu

在自动化运维和数据处理场景里，工程师长期面临一个落差：

  • cron 足够简单，但没有依赖关系、没有失败重试、没有执行历史，出了问题只能翻日志文件自己排查。
  • Airflow 能解决依赖和可观测性问题，但代价是要运维一整套平台——scheduler、元数据库、worker 集群、Python 环境，任务还必须改写成 Airflow 的 DAG 代码，产生框架耦合。
  • Temporal 提供了更强的持久化执行保证，但业务逻辑要迁移到它的 SDK 和编程模型里，侵入性更强。

Dagu 想填的正是中间这块空白：比 cron 强，但不需要像 Airflow / Temporal 那样交出基础设施主权和代码所有权。

设计哲学：配置而非代码

Dagu 最核心的设计原则是：工作流的结构是配置（YAML），任务本身的实现完全不感知 orchestrator 的存在。

换句话说，你的 shell 脚本、Python 脚本、Docker 镜像，不需要 import 任何 Dagu 的 SDK、不需要继承任何基类、不需要调用任何 Dagu 的 API。哪怕把 YAML 删掉，这些脚本依然可以独立运行、独立测试。Dagu 只是在外层加了一层"何时跑、按什么顺序跑、失败了怎么办"的编排逻辑。

实际价值：如果现在有一堆独立的脚本——数据处理脚本、模型转换脚本、同步脚本——用 Dagu 编排不需要重写任何脚本逻辑，只需要写一份 YAML 描述它们的先后关系和触发条件。迁移成本和回退成本都很低。

架构：一个二进制，四种角色

Dagu 的运行时被拆分为四种角色，但它们打包在同一个二进制文件里，可以合并运行在一台机器上，也可以拆开分布式部署：

SERVER

Server

提供 Web UI 和 REST API，用于查看 DAG 定义、触发运行、查看历史记录和日志。

SCHEDULER

Scheduler

负责 cron 定时调度和任务队列处理，决定"什么时候该跑哪个 DAG"。

COORDINATOR

Coordinator

gRPC 服务端点，供分布式 worker 轮询拉取任务；持久化运行状态、日志流、产物（artifacts）。

WORKER

Worker

轮询 coordinator 领取任务，在本地实际执行，并按标签（label）路由——比如把带 GPU 标签的任务只分配给有 GPU 的 worker。

这种"单二进制、角色可拆分"的设计，让 Dagu 既能作为一个几分钟装好的单机工具使用，也能在需要时扩展成分布式执行集群，而不需要更换软件栈。

三种部署模型

模型说明适合场景
Single Server一台机器跑全部角色（server + scheduler + coordinator + worker）个人自动化、小团队、单机批处理
Temporary Workersworker 按需临时创建（如 Cloud Run、K8s Job、CI runner），任务跑完即销毁，通过共享存储卷读写状态弹性伸缩、按量付费的云上批处理任务
Distributed Workers长期在线的 worker 常驻轮询 coordinator 领任务需要固定硬件资源（如特定 GPU 型号）的持续性任务

对需要弹性伸缩执行资源的场景而言，"Temporary Workers" 模型适合按需拉起节点跑一次性任务、再自动释放；"Distributed Workers" 则更适合长期占用固定资源池的持续性任务。

DAG 语法与核心字段

最基础的 DAG 定义非常简单：

# hello.yaml
steps:
  - id: hello
    run: echo "hello from Dagu"

一个更完整的 DAG 通常会用到以下字段：

字段作用
steps任务列表，每个 step 有 id、执行内容（run 或 action）
depends声明当前 step 依赖哪些其他 step，构成 DAG 边
params定义可传入参数（string/boolean/enum 等），Web UI 会自动生成表单
schedulecron 表达式，定时触发整个 DAG
retry_policy失败重试策略
continue_on指定失败后是否继续执行后续 step
handler_on生命周期钩子，如 failure、exit 时触发的处理逻辑
timeout_sec单 step 或整体超时时间
overlap_policy控制同一 DAG 是否允许并发重叠执行
catchup_window调度错过时间窗后的补跑策略
resources.limits限制 step 可用的 cpu、memory

并行与子工作流的写法：

steps:
  - id: fan-out
    action: dag.run
    with:
      dag: benchmark.yaml
    parallel:
      items: ["model-a", "model-b", "model-c"]
      max_concurrent: 2

这段配置会用不同的模型名参数并行调用 benchmark.yaml 子 DAG，同时最多并发 2 个——对批量跑多模型 benchmark 是个现成的模式。

Executor：能跑什么类型的任务

Dagu 的 step 不局限于 shell 命令，通过不同的 action 可以调用不同的执行器：

类型写法说明
Shellrun: <命令>直接执行任意 shell 命令，最基础的用法
Dockeraction: docker.run支持 image、pull、volumes、working_dir 等标准 docker run 参数
SSH顶层 ssh: 配置块指定 user/host/key，在远程主机上执行 step 中的命令
Kubernetes Job—官方文档中支持，具体字段建议查阅 docs.dagu.sh
Sub-DAGaction: dag.run调用另一个 DAG 作为子任务，可配合 parallel 做 fan-out
典型组合方式：同一个 pipeline 里，"本地跑数据预处理脚本"用 shell，"跑隔离环境任务"用 Docker 镜像，"操作远程主机"用 SSH，"调用 K8s Job 做分布式计算"用 K8s executor——不需要为每种执行环境单独搭一套调度系统。

关键特性

增量执行（Incremental Execution）

当命令和相关文件未发生变化时，可以复用上一次的执行结果；也能根据文件路径推断步骤之间的依赖关系，避免重复计算。这类似缓存复用的思路——只对发生变化的部分重新计算，避免每次全量重跑。

Human Tasks（人工确认节点）

工作流可以在某一步暂停，等待人工审核或输入后再继续。适合"高风险操作前需要人确认"的场景，比如生产环境变更前的审批。

密钥管理

内置日志掩码机制，防止密钥（API key、token）在日志输出中泄露。

可复现性

可以固定工具版本，worker 上自动安装与缓存，减少"本地能跑、线上跑不了"的环境漂移问题。

权限与 SSO（企业版）

RBAC 和 SSO 属于付费自托管许可证提供的能力，社区版不包含。

MCP Server

Dagu 提供 MCP（Model Context Protocol）Server，认证客户端可以通过 MCP 查询工作流状态、维护 Wiki、控制运行。这意味着 AI Agent 可以直接通过 MCP 协议触发和监控 Dagu 编排的 pipeline，把"执行层的可靠性"交给 Dagu，"决策层的判断"交给 Agent。

与 Airflow / Temporal / cron 的取舍

DaguAirflowTemporal
运维负担单二进制，几分钟启动需维护 scheduler + 元数据库 + worker + Python 环境需要托管 Temporal server 集群
任务定义方式纯 YAML，脚本零耦合要改写成 Python DAG 代码业务逻辑要用其 SDK 编程模型重写
对比 croncron 能跑命令，但没有依赖关系、没有重试、没有执行历史——这是 Dagu 想补上的短板

简单说：Airflow 换来的是强大的生态和调度能力，代价是平台化的运维成本和代码侵入；Temporal 换来的是跨进程的持久化执行保证，代价是编程模型迁移；Dagu 换来的是"轻量、零侵入、开箱即用"，代价是生态和高级调度能力不如前两者成熟。三者不是互相替代关系，而是根据团队规模和任务复杂度选型的问题。

实践示例：从零跑通一个 ETL Pipeline

第一步：安装

# macOS / Linux
curl -fsSL https://raw.githubusercontent.com/dagucloud/dagu/main/scripts/installer.sh | bash

# 验证安装
dagu version

第二步：跑通最小示例

创建 hello.yaml：

steps:
  - id: hello
    run: echo "Hello from Dagu!"
  - id: step_2
    run: echo "Running step 2"
    depends: hello
# 运行前先做静态校验，避免依赖写错、cron 表达式写错
dagu validate hello.yaml

# 试跑一次（dry run，不会真正执行副作用）
dagu dry hello.yaml

# 正式执行
dagu start hello.yaml

# 查看运行状态和历史
dagu status hello
dagu history hello

启动带 Web UI 的完整实例，访问 http://localhost:8080 查看可视化的 DAG 图和日志：

dagu start-all --dags .

第三步：一个接近生产的完整 ETL 示例

下面是官方文档给出的完整示例，覆盖了 cron 调度、条件判断、依赖链、重试、并行子任务、容器执行、失败通知等大部分核心能力，值得逐段读一遍：

description: Daily ETL pipeline for production data
labels:
  env: production
  type: etl
  priority: critical

schedule: "0 2 * * *"

max_active_steps: 5
timeout_sec: 7200
hist_retention_days: 90

params:
  - name: ENVIRONMENT
    default: production
  - name: DATE
    eval: "`date +%Y-%m-%d`"

env:
  DATA_DIR: /data/etl
  LOG_LEVEL: info

dotenv:
  - /etc/dagu/production.env

container:
  image: python:3.11-slim
  pull_policy: missing
  volumes:
    - ./data:/data
    - ./scripts:/scripts:ro

preconditions:
  - eval: "$(date +%u)"
    expected: "re:[1-5]"   # 只在工作日（周一到周五）运行

steps:
  - id: validate_environment
    run: ./scripts/validate.sh

  - id: extract_data
    run:
      - mkdir -p /data/raw
      - python extract.py --date="${params.DATE}" --output "/data/raw/${params.DATE}.json"
      - printf 'raw_data_path=%s\n' "/data/raw/${params.DATE}.json" >> "$DAGU_OUTPUT_FILE"
    outputs:
      - name: raw_data_path
    retry_policy:
      limit: 3
      interval_sec: 300
    depends: validate_environment

  - id: transform_data
    action: dag.run
    with:
      dag: transform_module
      params: "type=${ITEM} input=${steps.extract_data.outputs.raw_data_path}"
    parallel:
      items: [customers, orders, products]
      max_concurrent: 2
    depends: extract_data

  - id: load_data
    container:
      image: postgres:16
      env:
        PGPASSWORD: ${env.DB_PASSWORD}
    run: psql -h "${env.DB_HOST}" -U "${env.DB_USER}" -f load.sql
    depends: transform_data

  - id: validate_results
    run: python validate_results.py --date="${params.DATE}"
    mail_on_error: true
    depends: load_data

handler_on:
  success:
    run: ./scripts/notify-success.sh
  failure:
    action: mail.send
    with:
      to: data-team@example.com
      subject: "ETL failed - ${params.DATE}"
      message: "Check logs at ${context.paths.log_file}"
      attach_logs: true
  exit:
    run: ./scripts/cleanup.sh "${params.DATE}"

mail_on:
  failure: true

smtp:
  host: smtp.company.com
  port: "587"
  username: etl-notifications@company.com
  password: ${env.SMTP_PASSWORD}

---
name: transform_module
params:
  - name: type
    required: true
  - name: input
    required: true
container:
  image: python:3.11-slim
  volumes:
    - ./scripts:/scripts:ro
steps:
  - id: transform
    run: python /scripts/transform.py --type="${params.type}" --input="${params.input}"

这个示例值得注意的几个设计点：

  • preconditions 用 eval + 正则表达式做条件判断——只在工作日运行，周末自动跳过，不需要在脚本里写日期判断逻辑。
  • extract_data 步骤把结果路径写进 $DAGU_OUTPUT_FILE，下游步骤通过 ${steps.extract_data.outputs.raw_data_path} 引用——这是 Dagu 跨步骤传递数据的标准方式，下一节详细展开。
  • transform_data 用 parallel.items 对 customers/orders/products 三类数据并行跑同一个子 DAG，max_concurrent: 2 限制同时只跑两个，避免打爆数据库连接。
  • YAML 用 --- 分隔主 DAG 和子 DAG（transform_module），两者写在同一个文件里也是合法的。
  • handler_on 的 exit 钩子无论成功失败都会执行，适合做清理工作；failure 钩子直接用 action: mail.send 发邮件通知，不需要额外写通知脚本。

跨步骤数据传递

多步骤 pipeline 里一个绕不开的问题是：上一步的结果怎么传给下一步？Dagu 的机制是把输出写入一个特殊的环境变量指向的文件，再通过 outputs 声明成可引用的变量：

steps:
  - id: get_version
    run: |
      printf 'version=%s\n' "$(cat VERSION)" >> "$DAGU_OUTPUT_FILE"
    outputs:
      - name: version
  - id: build_image
    depends: get_version
    run: docker build -t "myapp:${steps.get_version.outputs.version}" .

引用语法固定为 ${steps.<step_id>.outputs.<output_name>}。多行输出（比如一份 markdown 报告）需要用 heredoc 定界符包裹，避免换行破坏解析：

steps:
  - id: summarize
    run: |
      {
        printf 'report<> "$DAGU_OUTPUT_FILE"
    outputs:
      - name: report

如果输出是结构化数据，可以声明类型为 JSON，方便下游按字段取值：

outputs:
  - name: metadata
    type: json
踩坑提醒：忘记在 run 命令里显式把结果写进 $DAGU_OUTPUT_FILE 是最常见的错误——outputs 字段只是声明"这个 step 会产出什么名字的变量"，真正写值的动作要脚本自己完成。如果只声明 outputs 但脚本没写文件，下游引用会拿到空值，而且不一定会报错，容易在流程跑通但结果不对的情况下被忽略。

调度细节：cron、补跑与队列

cron 表达式支持别名和时区，也支持一次性执行和多个时间窗：

schedule: "0 2 * * *"          # 每天 2AM
schedule: "@hourly"             # 别名，等价于 "0 * * * *"
schedule:
  - "0 9 * * MON-FRI"
  - "0 14 * * SAT,SUN"
schedule: "CRON_TZ=Asia/Tokyo 0 9 * * *"   # 带时区
schedule:
  - at: "2026-03-29T09:30:00+09:00"        # 一次性执行

调度器重启或宕机后，错过的运行怎么处理，由 overlap_policy 和 catchup_window 共同决定：

overlap_policy行为
skip（默认）丢弃错过的运行，直接跳到下一个调度点
all保留在缓冲区，下一个 scheduler tick 继续补跑
latest只保留最近一次错过的时间点，其余丢弃
 
schedule: "0 * * * *"
catchup_window: "6h"
overlap_policy: "skip"
steps:
  - run: ./hourly-job.sh
需要注意：catchup_window 生效的前提是在全局 config.yaml 里打开 queues.enabled: true，否则该字段不会起作用。补跑是按每个 scheduler tick（默认每分钟）补一个时间点，如果停机时间很长，补跑会持续一段时间才能追平，而不是瞬间执行完；每个 DAG 最多缓冲 1000 个错过的运行，超出会被丢弃。

并发控制可以用队列实现，避免同类型任务把资源打满：

# config.yaml
queues:
  enabled: true
  config:
    - name: batch-jobs
      max_concurrency: 2
# DAG 文件里指定使用哪个队列
queue: batch-jobs
schedule: "*/10 * * * *"
steps:
  - run: echo "Running batch process"

未指定 queue 时，DAG 默认使用本地队列，FIFO 执行，并发度为 1——这意味着同一个 DAG 的多次触发默认是排队串行的，不会自动并发。

错误处理与通知

重试策略支持指数退避，避免瞬时故障时的密集重试：

steps:
  - run: curl https://api.example.com/data
    retry_policy:
      limit: 5
      interval_sec: 2
      backoff: true          # 每次间隔翻倍
      max_interval_sec: 60    # 间隔上限
      # 实际间隔序列: 2s, 4s, 8s, 16s, 32s → 之后固定 60s

repeat_policy 和 retry_policy 容易混淆，但语义不同：retry_policy 是"失败了才重试"，repeat_policy 是"主动轮询直到满足条件"，典型用途是等待某个服务端口就绪：

steps:
  - run: nc -z localhost 8080
    repeat_policy:
      repeat: while
      exit_code: [1]
      interval_sec: 1
      backoff: 2.0
      max_interval_sec: 30
      limit: 20

生命周期钩子 handler_on 支持六种事件，exit 无论成功失败都一定会执行，适合做资源清理：

handler_on:
  init:
    run: acquire-lock.sh "${env.LOCK_NAME}"
  success:
    run: notify.sh "${context.dag.name} succeeded"
  failure:
    run: alert.sh "${context.dag.name} failed" "logs=${context.paths.log_file}"
  abort:
    run: rollback.sh --lock "${env.LOCK_NAME}"
  exit:
    run: rm -rf "/tmp/${context.run.id}"

邮件通知需要先配置全局 SMTP，再在 DAG 级别或 step 级别开启：

smtp:
  host: "smtp.gmail.com"
  port: "587"
  username: "${env.SMTP_USER}"
  password: "${env.SMTP_PASS}"

mail_on:
  failure: true
  success: false

error_mail:
  from: "dagu@company.com"
  to: "oncall@company.com"
  attach_logs: true

steps:
  - run: backup.sh
    mail_on_error: true
关于 Slack/Teams 等通知渠道：Web UI 的 Notifications 页面支持配置 Slack、Teams、Telegram 和 webhook 路由，但具体的 YAML 字段格式官方文档中未给出完整示例，需要在 Web UI 界面里实际配置查看，或者用 handler_on 里的 run: 调用自己写的通知脚本（如调用 Slack Incoming Webhook 的 curl 命令）作为替代方案。

CLI 命令一览

除了前面用到的 start/validate/dry/status/history，官方文档列出的常用命令还包括：

# 停止/重启/重试一个正在运行或已结束的工作流
dagu stop my-workflow
dagu restart my-workflow
dagu retry --run-id=20240101_120000 my-workflow

# 列出工作流、查看进程
dagu ps --dag my-workflow
dagu ls -n -l

# 按状态和时间范围过滤历史记录
dagu history my-workflow --status failed,aborted --last 7d

# 清理历史记录（保留 30 天内的）
dagu rm -H --older-than 30d my-workflow

# 单独启动某个角色（用于分布式部署）
dagu server --host=0.0.0.0 --port=9000
dagu scheduler --dags=/opt/dags
dagu coordinator --coordinator.host=0.0.0.0 --coordinator.port=50055
dagu worker --worker.labels gpu=true,memory=64G,region=us-east-1

# 入队/出队（配合队列并发控制使用）
dagu enqueue --queue=high-priority my-workflow.yaml
dagu dequeue default --dag-run=my-workflow:batch-001

# 其他工具类命令
dagu version
dagu config
dagu schema dag steps
dagu completion zsh
dagu upgrade --check
关于 retry 的一个细节：官方文档明确说明 dagu retry 会继承原始运行的 runtime profile（运行时配置），也就是说重试不是"从头用当前最新配置跑一遍"，而是尽量复现当时的运行环境——这对排查"为什么重试后结果不一样"的问题有帮助。

目录结构与最佳实践

默认目录布局：

~/.config/dagu/
├── dags/          # 工作流 YAML 文件
├── config.yaml    # 服务端配置
└── base.yaml      # 所有 DAG 共享的默认配置（公共 env、smtp 等可以放这里，避免每个 DAG 重复写）

~/.local/share/dagu/
├── logs/          # 每次运行的日志
├── data/          # 运行历史和状态
└── suspend/       # 暂停标志文件

如果需要统一迁移到自定义路径（比如挂载到某个数据盘），用环境变量整体覆盖比单独覆盖每个子路径更省心：

export DAGU_HOME=/opt/dagu              # 一次性覆盖 dags/logs/data 等全部路径
# 或者分别指定
export DAGU_DAGS_DIR=/workflows
export DAGU_LOG_DIR=/var/log/dagu
export DAGU_DATA_DIR=/var/lib/dagu
实践建议：把公共的 env、smtp、container 默认配置写进 base.yaml，各个 DAG 文件只写差异部分，能显著减少多个 pipeline 之间的重复配置，也方便统一改一处密钥或镜像版本。

实战经验与踩坑点

  • 先 validate 再 start：依赖写错步骤 ID、cron 表达式写错，dagu validate 都能在执行前拦下来，比等到跑起来才发现浪费的时间少得多。CI 流程里可以把 dagu validate 作为提交前的强制检查。
  • outputs 声明和实际写值是两件事：如上文所述，outputs 只是声明变量名，真正赋值要脚本自己往 $DAGU_OUTPUT_FILE 写。这是最容易被忽略、也最难排查的错误来源之一。
  • 不要混淆 retry_policy 和 repeat_policy："失败后重试"和"轮询直到满足条件"是两种不同的语义，用错了会导致该等待的地方直接报错退出，或者该失败退出的地方一直空转。
  • 并发默认是串行的：没有显式配置 queue 的 DAG，同一个 DAG 的多次触发默认 FIFO、并发度 1。如果观察到定时任务"堆积在排队"而不是并发跑，先检查是不是漏配了队列。
  • catchup_window 有全局开关依赖：只在 DAG 里写了 catchup_window 但没有在 config.yaml 里打开 queues.enabled: true，这个字段不会生效——这是一个容易被忽略的前置条件。
  • 先单机小步验证，再考虑分布式：建议先用 dagu start-all 单机跑通一个两三步的最小 DAG，确认依赖关系、输出传递、通知机制都符合预期后，再考虑拆分成 coordinator + worker 的分布式部署，避免一开始就在分布式环境里排查基础语法问题。
  • 敏感信息走 env + dotenv，不要写死在 YAML 里：示例中的数据库密码、SMTP 密码都是通过 ${env.XXX} 引用，配合 dotenv 从外部文件加载，避免明文密钥被提交进版本控制。

局限与注意事项

  • 生态成熟度：相比 Airflow 十年积累的 provider 插件生态，Dagu 作为较新项目，第三方集成和社区案例还在积累中。
  • 企业级能力需付费：RBAC、SSO、审计日志等企业治理能力属于付费自托管许可证，纯开源社区版不包含。
  • 分布式场景的成熟度：coordinator/worker 分布式架构相对新，大规模、高并发场景下的稳定性需要自行验证，不能直接假设等同于 Airflow/Temporal 的生产成熟度。
  • 没有独立的 FAQ/Troubleshooting 页面：官方文档站目前没有专门的故障排查栏目，遇到问题主要依赖 dagu validate 的报错信息、日志文件，以及查阅具体功能页面的说明。
  • Slack/Teams 等通知渠道的字段格式未完全公开：Web UI 里可以配置，但文档没有给出对应的 YAML/API 字段示例，需要在界面里实际操作确认。
